## Database schema and relationships

| Table          | Fields                                                                                                                                                      |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| integrations   | id, name, slug, provider, enabled, created_at, updated_at                                                                                                   |
| sync_runs      | id, integration_id, status, started_at, finished_at, records_received, records_persisted, records_failed, error_code, error_message, created_at, updated_at |
| source_records | id, sync_run_id, external_id, payload, source_updated_at, created_at                                                                                        |

All IDs are integer primary keys. Payload is non-null JSONB; timestamps use
`timestamptz`. Integration/run timestamps use Lucid's generated auto-create and
auto-update metadata. SourceRecord has only an auto-create timestamp.

Relationships: Integration has many SyncRuns; SyncRun belongs to Integration and
has many SourceRecords; SourceRecord belongs to SyncRun. SourceRecord reaches its
integration through its run and has no redundant integration foreign key.

Constraints and indexes:

- Unique `integrations.slug` and its backing index.
- Required FK `sync_runs.integration_id`, `ON DELETE RESTRICT`, with an explicit
  relationship index.
- Required FK `source_records.sync_run_id`, `ON DELETE RESTRICT`.
- Unique `(sync_run_id, external_id)` and its backing composite index; its leading
  column also supports queries by run, avoiding a redundant index.
- Status string check: PENDING, RUNNING, SUCCESS, PARTIAL, FAILED only.
- Non-null required fields; `enabled=true` and three counters defaulting to zero.
- Primary-key indexes. No speculative indexes.

## Isolation and tests

Created `data_integration_test` explicitly with PostgreSQL `createdb`. Test mode
selects `DB_TEST_DATABASE`, defaulting to that name. Configuration rejects names
without the `_test` suffix or names matching the development database before a
connection opens. A negative check using `DB_TEST_DATABASE=data_integration`
failed with the expected configuration error.

Japa runner setup uses `testUtils.db().migrate()` and its returned migration-reset
cleanup. Each persistence test uses `wrapInGlobalTransaction()` with automatic
rollback. These helpers suppress schema generation while testing, preserving the
generated schema artifact. After both local and Docker tests, only Lucid migration
metadata tables remained in the test database. Development still had all three
domain tables and zero rows; test fixtures never accumulated there.

Added 17 tests for integration persistence/timestamps/defaults/slug uniqueness;
run relationships/counters/null defaults/statuses/execution fields/FKs/deletion;
and source relationships/nested JSONB/date round trips/composite uniqueness/
cross-run observations/FKs/deletion. All three M0 bootstrap tests are unchanged.

RESTRICT preserves history instead of cascading deletion. JSONB preserves JSON
structure rather than exact HTTP bytes/key ordering. Append-only behavior and
lifecycle transitions are documented but intentionally unenforced. Counters are
persisted without cross-field accounting rules. Test cleanup resets the entire
isolated test schema; that database is disposable and not shared with unrelated
data or concurrent test runs.
