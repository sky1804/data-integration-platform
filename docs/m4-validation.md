## Installed API decisions

`@adonisjs/queue` remains exactly **0.6.2**, with locked underlying
`@boringnode/queue` **0.6.0**. Reviewed installed `Job`, `JobOptions`,
`JobDispatcher.run`, `DispatchResult`, `QueueManager.fake/restore`, `FakeAdapter`,
`Worker.processCycle`, Redis adapter and Adonis worker/provider implementations.
These installed APIs are authoritative for this experimental version.

`SyncIntegrationJob` extends `Job<{ integrationId: number }>` and simply awaits
`new SyncEngine().execute(this.payload.integrationId)`. It catches no exceptions
and performs no synchronization work itself. Options explicitly select the
default queue and `maxRetries: 0`, with no retry delay/backoff. The queue's default
immediate removal of finished jobs is overridden with bounded retention of 100
completed and 100 failed entries. SyncRun remains the independent PostgreSQL audit.

The controller awaits the package's dispatch acknowledgement and returns its real
jobId with HTTP 202, status queued and integrationId. It creates no SyncRun and
does not import or call SyncEngine. The engine's execution-time validation stays
authoritative because an integration may change while queued.

Invalid IDs return 400; missing integrations 404; disabled integrations 409;
unsupported providers 422. IDs must be canonical positive decimal integers within
the existing PostgreSQL integer range. Failed integration lookup and rejected
queue dispatch return sanitized 503 errors with INTEGRATION_UNAVAILABLE and
QUEUE_UNAVAILABLE respectively. No database/Redis details or stack traces enter
the JSON response.

Queue metadata uses pending/active/completed/failed; business execution uses
PENDING/RUNNING/SUCCESS/PARTIAL/FAILED. No run necessarily exists at enqueue time.
SUCCESS completes the job; any thrown engine failure fails it after business
finalization when possible. No queue-to-run schema link was introduced.

Existing discovery `./app/jobs/**/*.{ts,js}` and `node ace[.js] queue:work` find and
execute the job. Worker concurrency remains 5 and idle delay 2s. Redis remains the
real application backend. No deduplication, lock, single-flight execution,
scheduler, synchronization retry, authentication or new status/CRUD API is added.

## Automated tests and fake isolation

Dispatch tests use `queue.fake()` with `queue.restore()` registered as cleanup
after every test. Assertions cover real job identity/payload, real dispatched ID,
202 with no SyncRun/SourceRecords, invalid ID forms, missing/disabled/unsupported
integrations, sanitized failed queue push, lookup outage and two distinct jobs for
two accepted requests. These tests do not execute the provider.

No official high-level job testing helper exists in the installed package.
Execution tests instead use its supported Worker.processCycle API and official
underlying FakeAdapter, letting the worker hydrate and execute the actual class.
They do not call internal job hydration or implement a production worker loop.
The prior manager adapter/factory/logger/config and job discovery are restored
after each case. Real local mock HTTP and the guarded PostgreSQL test database
verify SUCCESS plus three records, provider failure plus failed queue state and
FAILED audit, and an integration disabled after dispatch failing before provider
access or run creation. Queue attempts stay zero; no job is requeued.

M1 retains global transactional test isolation. Worker tests use M3's isolated
test-database truncation strategy for real page transactions. Functional migration
and cleanup guards are unchanged. The full suite verifies fake state does not
leak into existing tests.

## Real Redis and separate worker validation

`npm run test:async` uses the built production image and existing Compose
infrastructure. It creates a unique `m4_validation_<timestamp>_test` PostgreSQL
database, a dedicated Redis container, and a validation API on a random localhost
port. API/worker use NODE_ENV=test and DB_TEST_DATABASE explicitly. Their Redis
host is the disposable Redis container; the normal worker cannot consume those
jobs. Provider credentials are changed only on the disposable failure worker.

Observed sequence:

1. With no validation worker running, HTTP POST returns 202. The actual Redis
   adapter reports the job pending with payload containing only integrationId;
   no SyncRun or SourceRecord exists.
2. Starting a separate standard worker consumes that job. Its Redis record becomes
   completed, exactly one SUCCESS run exists and three SourceRecords are stored.
3. After stopping that worker, another POST returns 202. A separate worker with
   deliberately invalid Carrier credentials consumes it. The queue record becomes
   failed and a second run remains FAILED/PROVIDER_AUTHENTICATION with zero stored
   records. The original request remains 202. No automatic retry occurs.
4. With the dedicated Redis container stopped, another request returns sanitized
   503/QUEUE_UNAVAILABLE and creates no new run.
5. Development table counts match their initial values (zero in all three domain
   tables). Only recorded container IDs belonging to the invocation are removed;
   the owned `_test` database is dropped after process cleanup. No shared Redis
   keys are deleted and no FLUSHALL/FLUSHDB command is used.

The script's bounded waits and assertions fail on incomplete execution. Cleanup
runs on failures as well. It requires Node.js 24, Docker, healthy Compose
infrastructure, applied development schema, and an already built production
image. It does not replace the fast regular suite or require a hosted API.

## Issues and remaining tradeoffs

Initial real outage checks used a short client deadline and encountered a closed
connection/timeout while Redis's existing reconnect policy was still running.
The validation client now uses fresh HTTP connections and a 60s deadline; actual
503 handling passes without changing application Redis retry configuration.
Dispatch outage response time therefore follows the existing connection policy
and can take tens of seconds. This is infrastructure connection recovery, not
synchronization job retry.

Running the production image with NODE_ENV=test can log a route-type generation
permission warning because generated build files are root-owned. Framework logs
this as nonfatal; validation HTTP and worker execution succeed. Normal production
API/worker startup is clean and no longer emits the old no-jobs warning.

The endpoint is unauthenticated and permits concurrent duplicate requests.
Queue history is bounded and no durable queue-job/SyncRun linkage exists. Crashes
can leave RUNNING audits; stalled-job recovery and uncertain enqueue
acknowledgements do not provide exactly-once execution. Business retry/idempotency,
stale-run recovery, deduplication, locking and status APIs remain later concerns.

Existing install audit counts remain 17 high-rated affected entries in the full
graph and 13 in production; dependencies/lockfile were retained. See the dated
[dependency security review](dependency-security.md). No dependency fix is mixed
into this feature.

No M5+ functionality was implemented. No automatic job retries/backoff, scheduler,
locks, generic Connector, TMS, normalization, reconciliation, authentication,
frontend or CI/CD was added.

Reference: [current AdonisJS Queue guide](https://docs.adonisjs.com/guides/digging-deeper/queues),
cross-checked against the installed pinned package rather than assuming newer APIs.
