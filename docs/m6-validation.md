## Final design

NormalizedShipment is one historical projection per SourceRecord produced by the
M6 SyncEngine path. Its canonical fields are shipmentKey, status, and amount.
Its required unique source_record_id foreign key uses ON DELETE RESTRICT;
SourceRecord hasOne NormalizedShipment and the projection belongsTo SourceRecord.
The database enforces status membership and required source/key/status/amount.

Carrier maps shipmentId/amount and passes PENDING, IN_TRANSIT, DELIVERED, CANCELED
to the same canonical statuses. TMS maps shipmentCode/totalValue and
CRIADO → PENDING, EM_TRANSITO → IN_TRANSIT, FINALIZADO → DELIVERED,
CANCELADO → CANCELED. All other status strings map to UNKNOWN without failure.
Raw payloads retain their original fields, statuses, date strings, and extra data.

Amounts use PostgreSQL numeric(15,2), with Lucid-generated TypeScript string
typing and driver string reads. The shared conversion pads two decimal places
without rounding; values with extra fractional digits, nonfinite values, and
out-of-range values are rejected. Negative amounts remain supported. The bound is
±9,999,999,999,999.99. No currency is invented. TMS deliveryDate remains raw;
Carrier updatedAt is not a delivery date.

Normalizers are pure and separate from Connector. SyncEngine creates each raw
record and projection through the same page transaction client, followed by the
progress update. A normalization or canonical insert failure rolls back the
entire page and marks all its records failed. Earlier committed pages remain.
Unknown statuses do not fail. Unrepresentable amounts use a fixed sanitized
NORMALIZATION_ERROR; canonical database failures retain PERSISTENCE_ERROR.
No provider values, credentials, SQL text, connection details, or stack traces
are copied into public/audit failures.

Repeated runs preserve separate raw and normalized observations. The migration
creates an empty table without a backfill. Existing historical sources can have
no projection; at-most-one linkage is database-enforced, while creation of both
records together is enforced by the M6 ingestion transaction.

## Issues and remaining tradeoffs

The first migration attempt used an unsupported Knex column CHECK modifier;
changing it to a table CHECK fixed the migration. Initial lint found awaited
member access and formatting in the new tests; these were corrected and lint
passed. Docker emitted a nonfatal engine-pipe message during build. Production npm
installation still reports the existing 13 high-severity findings; no dependency
or lockfile upgrade was made.

Numeric input has already passed through JSON.parse/JavaScript number before
normalization: original wire spelling or lost precision cannot be recovered.
The no-rounding guard validates the parsed number's shortest decimal form;
direct SQL writes to numeric(15,2) can round and must not bypass ingestion
validation in future write paths. No DB trigger enforces a mandatory child for
historical SourceRecords. No backfill, current-state table, currency, delivery
date normalization, alerting, lock, retry, recovery, or reconciliation is added.
Existing concurrent-run and recovery limitations remain.

M6 is complete. No reconciliation, discrepancy processing, or other M7
functionality was implemented. M7 has not been started.
